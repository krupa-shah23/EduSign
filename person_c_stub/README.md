# person_c_stub

**This is an interface stub, not the research model.**

Its only purpose is to unblock Person D's Month 1 robustness module (hold-
last-value handling, face/head-size normalisation, latency timing) by
giving them a stable, documented landmark format to build against — before
the transformer encoder / recognition model exist.

It contains:
- No transformer
- No training loop
- No SignBERT / SHuBERT / WLASL preprocessing
- No model code of any kind

Just: video/webcam → MediaPipe Holistic → landmarks on disk, in a fixed
format.

## Contents

```
person_c_stub/
    capture.py                 # webcam/video -> MediaPipe Holistic results
    export_landmarks.py        # results -> fixed-shape tensor -> disk (.npy + .json)
    generate_sample_data.py    # synthetic sample recordings (see note below)
    landmark_schema.md         # the interface contract — READ THIS FIRST
    sample_landmarks/          # 5 ready-to-use sample recordings
    README.md                  # this file
```

Start with **`landmark_schema.md`** — it fully specifies the tensor shape,
landmark ordering, coordinate system, and missing-value convention. This
README covers how to run the code; the schema doc covers how to consume
the output.

## Quick start for Person D

You don't need to run any code to get started — six sample recordings are
already in `sample_landmarks/`. Load one like this:

```python
import json
import numpy as np

name = "sample01_normal_signing"
landmarks = np.load(f"sample_landmarks/{name}_landmarks.npy")    # (150, 543, 3)
timestamps = np.load(f"sample_landmarks/{name}_timestamps.npy")  # (150,)
meta = json.load(open(f"sample_landmarks/{name}_metadata.json"))

# Access the new metadata fields:
schema_version = meta["schema_version"]  # 1
image_width = meta["image_width"]
image_height = meta["image_height"]
```

See `landmark_schema.md` §7 for the full loading example, including how to
slice out individual landmark groups (face / pose / left hand / right hand)
using the metadata rather than hardcoded indices.

## The six sample recordings

| File prefix                         | Scenario                                                        |
|--------------------------------------|-------------------------------------------------------------------|
| `sample01_normal_signing`            | Steady two-handed motion, no dropout (synthetic)                 |
| `sample02_fast_signing`              | Higher-frequency, larger-amplitude hand motion (synthetic)       |
| `sample03_left_hand_occlusion`       | Left hand landmarks NaN for frames 60–99 (synthetic)             |
| `sample04_right_hand_occlusion`      | Right hand landmarks NaN for frames 40–89 (synthetic)            |
| `sample05_low_light_degradation`     | Noise + scattered short dropouts across all groups (synthetic)   |
| `real_webcam_signing`                | Real webcam capture (20–30 seconds of natural signing)           |

These cover the failure modes the robustness module needs to handle:
sustained single-hand occlusion (03, 04) and noisy/intermittent tracking
loss across all landmark groups (05), plus two "clean" baselines (01, 02)
at different motion speeds. The real webcam sample (06) provides ground
truth for format validation.

### Synthetic vs. real samples

**Samples 01–05** were generated by `generate_sample_data.py`, which
fabricates plausible-looking coordinate trajectories and applies dropout
patterns matching each scenario — **they do not run MediaPipe**.

What *is* real: they are written using the exact same
`export_landmarks.save_recording()` function that real captures use, so
the file format, shapes, dtypes, and metadata are byte-for-byte what a real
capture would produce. Person D can build and test the robustness module
against these today with zero format risk.

**Sample 06** (`real_webcam_signing`) is captured directly from a real
webcam using the standard `export_landmarks.py` pipeline, validating that
the interface contract works end-to-end with actual MediaPipe results.

When a video file becomes available, regenerate any sample with:

```bash
# from a video file
python export_landmarks.py <name> --video path/to/clip.mp4

# from a live webcam, capturing 20–30 seconds (~600–900 frames at 30 FPS)
python export_landmarks.py <name> --max-frames 750 --output-dir sample_landmarks
```

Nothing in Person D's code needs to change when this happens — the output
format is identical either way.

## Running the real capture pipeline

Requirements: `mediapipe` (with the legacy `solutions` API — some minimal
mediapipe builds only ship the newer Tasks API and won't work here),
`opencv-python`, `numpy`.

```bash
pip install mediapipe opencv-python numpy
```

**From a video file:**
```bash
python export_landmarks.py <name> --video path/to/video.mp4 --output-dir sample_landmarks
```

**From a webcam** (`--max-frames` is required since a live feed has no
natural end point):
```bash
python export_landmarks.py <name> --max-frames 300 --output-dir sample_landmarks
```

**Programmatically**, for custom pipelines:
```python
from export_landmarks import record_from_source, save_recording

landmarks, timestamps, fps, image_width, image_height = record_from_source("path/to/video.mp4")
save_recording(
    "my_recording", 
    landmarks, 
    timestamps, 
    fps, 
    "sample_landmarks",
    image_width=image_width,
    image_height=image_height,
)
```

## Design notes

- **Fixed 543-point layout** (face 468 + pose 33 + left hand 21 + right
  hand 21) matches MediaPipe Holistic's own total point count, so no
  landmarks are dropped or re-indexed — Person C's code is a thin,
  auditable pass-through, not a reinterpretation of MediaPipe's output.
- **Whole-group NaN on missing detection** (never zero, never
  hold-last-value) — hold-last-value is explicitly Person D's
  responsibility, not baked in here, so it stays testable and swappable.
- **Raw MediaPipe normalised coordinates**, unmodified — face/head-size
  normalisation is explicitly Person D's job, not duplicated here.
- **Timestamps stored separately from the landmark tensor** so latency
  timing can be computed without touching the landmark data itself.

See `landmark_schema.md` for the full, versioned contract.
